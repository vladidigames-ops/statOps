# Архитектура statOps

> Документ описывает общий замысел системы: какие задачи решает, из чего
> состоит, как устроены данные, как добавляются новые источники, как
> работает безопасность и развёртывание. Это рабочий документ — он будет
> обновляться по ходу проекта.

## 1. Видение

statOps — это **аналитическая надстройка над POS-системами общепита**.
Она:

1. Регулярно забирает данные из подключённых источников (продажи,
   номенклатура, себестоимость).
2. Принимает данные о расходах (руками, через CSV, через API банка/1С).
3. Строит отчёты в едином виде: выручка, ABC по блюдам, foodcost, маржа,
   P&L.
4. Отдаёт всё это владельцу через веб-интерфейс и выгрузки в Excel.

Ключевая идея — **унифицированная модель данных**. Продажа из iiko и
продажа из Quick Resto после загрузки выглядят одинаково, и вся бизнес-
логика отчётов работает с этой унифицированной моделью, не зная,
откуда пришли данные.

## 2. Слои системы

```
┌──────────────────────────────────────────────────────────┐
│  Frontend (React + Refine + Mantine)                     │
│  Дашборды, формы расходов, настройки источников, экспорт │
└────────────────────────┬─────────────────────────────────┘
                         │ REST API + JWT
┌────────────────────────▼─────────────────────────────────┐
│  Backend (FastAPI)                                       │
│                                                          │
│  ┌─────────────┐ ┌─────────────────┐ ┌────────────────┐  │
│  │ API layer   │ │ Service layer   │ │ Export layer   │  │
│  │ /api/v1/... │ │ reports, sync,  │ │ openpyxl       │  │
│  │             │ │ cost-calculator │ │ → .xlsx        │  │
│  └─────────────┘ └─────────────────┘ └────────────────┘  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Connectors                                       │    │
│  │  ├─ iikoCloud                                    │    │
│  │  ├─ QuickResto                                   │    │
│  │  └─ Bank / 1C / МойСклад (поэтапно)              │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Workers (Celery): инкрементальная синхронизация  │    │
│  └──────────────────────────────────────────────────┘    │
└────────────────────────┬─────────────────────────────────┘
                         │
       ┌─────────────────┼──────────────────┐
       ▼                 ▼                  ▼
  PostgreSQL          Redis             Файловое
  - operational      - очередь          хранилище
  - raw payloads     - кэш отчётов      (выгрузки)
  - unified
```

### Зачем такое разделение

- **Connectors** изолированы — у каждого свой код, свои настройки, свои
  ошибки. Если завтра iiko сломает API, чинится один модуль.
- **Service layer** работает только с унифицированной моделью данных.
  Это значит, что отчёт «Foodcost» написан один раз и работает для
  любой POS, которую мы подключим.
- **Raw payloads** хранятся отдельно. Это страховка: если мы захотим
  пересчитать историю по новым правилам, нам не нужно заново тянуть
  всё из POS.

## 4. Модель данных (унифицированная)

Это сердце системы. Все коннекторы маппят свои данные в эти таблицы.

### 4.1. Тенантизация

```
Account (1) ──< User (N)
Account (1) ──< Establishment (N) ──< Source (N)
```

- **Account** — владелец платформы (физическое или юридическое лицо).
- **User** — конкретный пользователь, имеет роль внутри Account.
- **Establishment** — заведение (ресторан, кофейня и т.д.).
- **Source** — подключённый источник данных конкретного заведения
  (например, «iikoCloud для нашего ресторана»).

Любая бизнес-сущность (продажа, расход, продукт) принадлежит
`establishment_id`, который через `account_id` относится к тенанту.
Изоляция тенантов реализуется на сервисном слое (см. §6).

### 4.2. Каталог

| Таблица | Поля (основные) | Описание |
|---|---|---|
| `accounts` | id, name, created_at | Тенант |
| `users` | id, account_id, email, password_hash, role, created_at | Пользователи (owner / manager / accountant / viewer) |
| `establishments` | id, account_id, name, type, timezone, currency | Заведение |
| `sources` | id, establishment_id, type, credentials_encrypted, status, last_sync_at | Подключённые POS/CRM |
| `products` | id, establishment_id, source_id, external_id, name, category, current_price, is_dish | Унифицированная номенклатура |
| `product_categories` | id, establishment_id, name, parent_id | Категории блюд |
| `sales` | id, establishment_id, source_id, external_id, opened_at, closed_at, total, payment_type, waiter_id, table_id, guests | Чек |
| `sale_items` | id, sale_id, product_id, quantity, unit_price, discount, total, cost_at_sale | Позиции в чеке |
| `cost_snapshots` | id, product_id, effective_date, unit_cost, source | История себестоимости |
| `expense_categories` | id, account_id, name, parent_id, kind (fixed/variable) | Дерево категорий расходов |
| `expenses` | id, establishment_id, date, category_id, amount, description, source (manual/csv/bank/...), external_ref | Расход |
| `sync_runs` | id, source_id, started_at, finished_at, status, payload_count, error | Журнал синхронизаций |
| `raw_payloads` | id, source_id, fetched_at, kind, payload_jsonb | Сырьё для пересчёта |

### 4.3. Особенности

- **`cost_at_sale`** — себестоимость фиксируется в момент продажи, чтобы
  ретроспективные изменения цен не искажали историю.
- **`raw_payloads`** — JSONB-копии ответов от POS API. Берут место, но
  страхуют от потери данных и позволяют пересчёт.
- **`sync_runs`** — журнал для диагностики. По нему видно, когда какой
  источник синхронизировался и были ли ошибки.

## 5. Источники данных

См. подробнее в [`INTEGRATIONS.md`](INTEGRATIONS.md). Кратко:

| Источник | Что тянем | Как |
|---|---|---|
| iikoCloud | Продажи (OLAP), номенклатура, себестоимость, сотрудники | REST, инкрементально по дате, раз в N часов |
| Quick Resto | Продажи, продукты | REST, инкрементально |
| Банк (Тинькофф/Сбер) | Расходы из выписки | OAuth2, по расписанию |
| МойСклад / 1С | Документы расходов | API соответствующей системы |
| Ручной ввод / CSV | Расходы, любые корректировки | Веб-интерфейс |

### Интерфейс коннектора (упрощённо)

```python
class Connector(Protocol):
    async def test_connection(self) -> bool: ...
    async def fetch_products(self) -> list[ProductRaw]: ...
    async def fetch_sales(self, since: datetime) -> list[SaleRaw]: ...
    async def fetch_costs(self, since: datetime) -> list[CostRaw]: ...
```

Реализации (`IikoCloudConnector`, `QuickRestoConnector` и т.д.) приводят
свои данные к `*Raw`-объектам, а ETL-слой переводит их в унифицированные
сущности.

## 6. Multi-tenancy

**Подход — shared schema with tenant column.** Все таблицы бизнес-сущностей
имеют (прямо или через FK-цепочку) ссылку на `account_id`.

- **На сервисном слое** все запросы проходят через `TenantContext`,
  который автоматически добавляет фильтр по `account_id` текущего
  пользователя.
- **На уровне БД** — индексы `(account_id, …)` на ключевых таблицах для
  быстрых выборок и нечастых full scan.
- **Запрет cross-tenant запросов** — статическая проверка плюс юнит-тесты,
  убеждающиеся, что сервисы не могут случайно вернуть чужие данные.

Это проще, чем schema-per-tenant или DB-per-tenant, и при правильно
выставленных индексах легко тянет десятки тенантов на одной инстанции.

## 7. Расчёт себестоимости (MVP)

На старте идём по простому пути: **берём готовое из iiko OLAP**.

- Запрашиваем OLAP-отчёт с полями `productCostBase` и `productCostAverage`
  по выбранным датам.
- Сохраняем в `cost_snapshots` по дате.
- При записи `sale_items` берём актуальный `cost_snapshot` на дату
  продажи и фиксируем в `cost_at_sale`.

В будущем (Спринт 8+) можно перейти на собственный расчёт из тех. карт
и закупок — данные для этого мы уже храним в `raw_payloads`.

## 8. Расходы

Модуль расходов — собственный, независимый от POS.

- **Категории** — дерево, владелец редактирует под себя (есть стартовый
  набор: аренда, ФОТ, коммуналка, маркетинг, продукты, прочее).
- **Источники записи:**
  - Ручной ввод через веб-форму.
  - Импорт из CSV/Excel с маппингом колонок.
  - **(Поздние спринты)** Банк через API → автоматическая разметка по
    правилам.
  - **(Поздние спринты)** МойСклад/1С — синхронизация документов расходов.
- **Распределение между заведениями** — если расход общий (например,
  юрлицо платит аренду за два кафе), указывается доля.

## 9. Отчёты

Каждый отчёт — это сервис, который собирает параметры (период, заведение,
фильтры) и возвращает структурированные данные.

Список отчётов MVP:

### 9.1. Выручка и чеки

- Выручка (Σ `sale.total`), кол-во чеков, средний чек, кол-во гостей,
  чек на гостя.
- Срезы: по дням, неделям, месяцам, часам, дням недели.
- Сравнение период-к-периоду.
- Срезы по способу оплаты, по официантам, по залам.

### 9.2. ABC-анализ продуктов

- Сортируем продукты по выручке за период.
- A — первые 80% выручки, B — 80–95%, C — 95–100%.
- Параллельно — по марже.
- Также: топ-N по количеству, топ-N по абсолютной марже.

### 9.3. Foodcost и маржа

- Foodcost % = Σ `cost_at_sale` / Σ `total` × 100.
- Маржа абс. = `total − cost_at_sale`.
- Маржа % = маржа / total × 100.
- Срезы: по блюду, по категории, по периоду.
- Динамика foodcost по неделям/месяцам (раннее предупреждение о росте
  закупочных цен).

### 9.4. P&L

- Выручка − Foodcost = Валовая маржа.
- Валовая маржа − Расходы (по категориям) = Операционная прибыль.
- По месяцам, кварталам, годам.
- Поддержка нескольких заведений суммой.

### 9.5. Экспорт

- Любой отчёт → кнопка «в Excel» → шаблон в `templates/excel/<report>.xlsx`,
  заполняется через openpyxl.
- Также CSV-выгрузка сырых данных по фильтрам (для бухгалтера).

## 10. Frontend

Подход — **Refine как каркас + Mantine как UI**.

- **Refine** даёт: роутинг, AuthProvider, DataProvider под наш REST API,
  готовые CRUD-страницы (списки/формы), notifications, i18n.
- **Mantine** даёт: компоненты (таблицы, формы, даты, графики через
  `@mantine/charts`), хорошая стилизация из коробки.
- **Структура страниц**:
  - `/login`, `/register`
  - `/dashboard` — главная с ключевыми метриками
  - `/establishments` — управление заведениями
  - `/sources` — подключение POS-источников
  - `/reports/revenue` — отчёт по выручке
  - `/reports/abc` — ABC-анализ
  - `/reports/foodcost` — foodcost и маржа
  - `/reports/pnl` — P&L
  - `/expenses` — модуль расходов
  - `/settings` — пользователи, роли, общие настройки

## 11. Безопасность

- **Пароли** — Argon2id с солью.
- **Сессии** — JWT (короткий access + refresh), хранение в HttpOnly cookie.
- **Credentials к POS** — шифрование AES-256 (Fernet) ключом из env;
  ключ не лежит в репозитории, в проде — из секрет-менеджера.
- **RBAC** — роли: `owner` (всё), `manager` (всё кроме настроек тенанта),
  `accountant` (отчёты + расходы), `viewer` (только чтение).
- **Аудит** — критичные действия (подключение/удаление источников,
  изменение пользователей) пишутся в `audit_log`.
- **HTTPS** — обязательно в проде. В compose — Caddy/Traefik с автоTLS.
- **CSRF** — для cookie-based auth; либо переходим на header-based JWT
  для SPA.
- **CORS** — белый список доменов в конфиге.

## 12. Развёртывание

### Локально (для разработки)

```yaml
# docker-compose.yml (черновик)
services:
  postgres: ...
  redis: ...
  api: ...        # FastAPI
  worker: ...     # Celery worker
  beat: ...       # Celery beat (расписание)
  frontend: ...   # Vite dev server
  caddy: ...      # обратный прокси с TLS
```

Команды: `make up`, `make logs`, `make migrate`, `make test`.

### В продакшн (когда дозреем)

- Российский провайдер (Yandex Cloud / Selectel).
- Управляемый Postgres + Redis.
- Frontend как статика на S3-совместимом хранилище.
- Backend в Compute / VM с docker-compose, потом — k8s, если будет много
  тенантов.

## 14. Открытые вопросы

Эти решения мы примем, когда дойдём до соответствующих спринтов:

- **Часовые пояса.** У заведения свой `timezone`, но как агрегировать
  отчёты по сети с разными часовыми поясами? Скорее всего — всё в UTC
  внутри, конвертация при выдаче.
- **Валюты.** На MVP — только RUB. Поддержка нескольких валют — позже.
- **Списания и возвраты.** В iiko OLAP они есть, но представление в
  отчётах надо обсудить отдельно.
- **«Реальное» vs. фискальное.** Бывает, что часть выручки идёт мимо
  кассы; платформа должна позволять корректировки, но не подменять
  собой ОФД.
- **Прогнозы.** ML-надстройка (предсказание выручки, рекомендации по
  меню) — отдельный пласт, для него мы уже создаём предпосылки правильным
  хранением raw + унифицированной модели.
