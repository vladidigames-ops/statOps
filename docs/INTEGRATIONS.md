## 1. iikoCloud API

**Основной источник данных в MVP.**

### Аутентификация

iikoCloud (раздел Cloud Business Logic, бывший iikoTransport / iiko.biz)
выдаёт API-логин:

1. В личном кабинете iiko создаётся API-логин с правами на нужные
   организации.
2. Авторизация: `POST /api/1/access_token` с `apiLogin` →
   возвращается `correlationId` + `token`.
3. Токен живёт ~1 час, обновляется по мере необходимости.

Дополнительно для каждого запроса нужен `organizationId` — идентификатор
заведения внутри iiko.

### Эндпоинты, которые нам нужны

| Группа | Эндпоинт | Что даёт |
|---|---|---|
| Орг-ция | `POST /api/1/organizations` | Список доступных заведений |
| Номенклатура | `POST /api/1/nomenclature` | Категории, группы, блюда, тех. карты |
| Меню | `POST /api/2/menu/by_id` | Текущее меню с ценами |
| OLAP продажи | `POST /api/2/reports/olap` (`reportType=SALES`) | Чеки, позиции, выручка |
| OLAP транзакции | `POST /api/2/reports/olap` (`reportType=TRANSACTIONS`) | Кассовые операции, оплаты |
| OLAP товародвижение | `POST /api/2/reports/olap` (`reportType=DELIVERIES`) | Закупки, списания |
| Сотрудники | `POST /api/1/employees` | Официанты, для срезов |
| Столы | `POST /api/1/reserve/available_restaurant_sections` | Залы, столы |

### OLAP — главный инструмент

OLAP-эндпоинт позволяет запросить любую таблицу с произвольным набором
полей и фильтров. Это самое мощное, что есть в iiko API. Для отчёта
«продажи» мы запрашиваем поля:

- `OpenDate.Typed`, `CloseDate.Typed` — даты
- `OrderNum` — номер чека
- `DishName`, `DishCategory.Name`, `DishGroup.Name`
- `DishAmountInt`, `DishDiscountSum`, `DishDiscountSumInt`
- `DishSumInt` — сумма позиции
- `ProductCostBase.ProductCost` — себестоимость
- `PayType`, `PayTypes.Combo`
- `WaiterName`, `TableNum`, `GuestNum`

С фильтром по `OpenDate` за инкрементальный период.

### Стратегия синхронизации

- **Первоначальный импорт** — за последние 3 месяца (настраиваемо).
- **Регулярная** — Celery beat раз в час, забираем чеки, закрытые после
  `last_sync_at`.
- **Поправочный проход** — раз в сутки забираем чеки за последние 7 дней
  заново: чеки могут модифицироваться (возвраты, корректировки) после
  закрытия.
- **Сырые ответы** — каждое возвращённое тело OLAP пишется в
  `raw_payloads` целиком (JSONB).

### Ограничения и подводные камни

- OLAP может возвращать много данных; ограничение по объёму ответа —
  батчим по неделям при первичной загрузке.
- Время в ответах — в часовом поясе организации, не UTC. Конвертация
  на стороне коннектора.
- Поля `ProductCostBase.ProductCost` могут быть пустыми для блюд без
  тех. карты — обрабатываем как `NULL`.
- Иногда iiko присылает «лишние» строки (например, технические записи).
  Фильтрация по `OrderType` или `Storno` обязательна.

### Документация

- Официальный портал: https://api-ru.iiko.services/ (Cloud Business Logic).
- Версии API регулярно меняются — фиксируем версию в конфиге коннектора.

## 2. Quick Resto API

**Подключаем в Спринте 6.**

### Аутентификация

- API-ключ выдаётся в кабинете заведения.
- Передаётся как `Authorization: Bearer <token>` либо как query-параметр
  (зависит от метода — уточняется при реализации).

### Эндпоинты, которые нам интересны

| Группа | Эндпоинт (примерно) | Что даёт |
|---|---|---|
| Продукты | `GET /api/v1/products` | Номенклатура |
| Чеки | `GET /api/v1/receipts` или `/api/v1/sales` | Продажи |
| Категории | `GET /api/v1/product-categories` | Структура меню |
| Сотрудники | `GET /api/v1/employees` | Срезы |
| Склад | `GET /api/v1/warehouse/*` | Закупки/списания |

**Точные эндпоинты и поля уточняем при реальной интеграции** — у QR
документация в кабинете, и она меняется. План в архитектурном смысле
не зависит от точных названий: ETL приведёт всё к нашей унифицированной
модели.

### Webhooks

Quick Resto умеет присылать вебхуки при событиях (новый чек, закрытие
смены). Это альтернатива поллингу, и она лучше — данные приходят в
реальном времени.

Подход:

- На стороне платформы делаем `POST /webhooks/quickresto/{source_id}`.
- Подписываемся в кабинете QR на нужные события.
- Получаем событие → сохраняем raw → асинхронно ETL → обновляем
  унифицированную модель.

Поллинг оставляем как fallback на случай пропущенных вебхуков.

## 3. Расходы из банка (Тинькофф / Сбер)

**Спринт 7.**

### Тинькофф Бизнес API

- OAuth2 поток.
- Эндпоинты выписок (`bank-api.tinkoff.ru`).
- Получаем операции с описанием, контрагентом, суммой, датой.
- Категоризация — по правилам (регулярки/ключевые слова в описании →
  категория) + ручная разметка непонятных.

### Сбер Бизнес API

- Аналогичная история, но через свой кабинет/SDK.
- Часть функций требует УКЭП — это нужно учесть в архитектуре
  подключения.

### Архитектурно

- Банк — это тоже `Source` со своим `type` и шифрованными credentials.
- ETL банка пишет не в `sales`, а в `expenses` (или в отдельный
  `bank_transactions` со связью на `expense`, если потребуется
  разделение).

## 4. МойСклад

**Спринт 8.**

- REST API: https://dev.moysklad.ru/
- Авторизация: Basic Auth или Bearer.
- Тянем `entity/expenseitem`, `entity/purchaseorder`, `entity/payout`
  и прочие документы расходов.
- Маппинг статей затрат МойСклада → наши категории расходов
  (настраивается владельцем).

## 5. 1С

**Спринт 9.**

- Самый сложный случай: 1С у каждого настроена по-своему.
- Стандартные пути:
  - ODATA-сервис из 1С (`/odata/standard.odata/`).
  - Или web-сервис, сделанный программистом 1С.
- Решение по типу подключения — для конкретного клиента.
- На MVP заложен только интерфейс коннектора; реальная реализация —
  под пилот.

## 6. Ручной ввод / CSV / Excel

Не интеграция в инженерном смысле, но важный «источник»:

- Форма «новый расход» с категорией, датой, суммой, описанием,
  заведением(ями).
- Импорт CSV: загрузка файла, превью первых строк, маппинг колонок
  (категория, дата, сумма, …), сохранение шаблона маппинга, импорт.
- Откат: каждый импорт получает `import_batch_id`, и его можно отменить
  целиком.
