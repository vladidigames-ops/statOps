# План MVP

> План разбит на спринты по ~2 недели. Каждый спринт заканчивается
> **работающим инкрементом**: что-то, что уже можно посмотреть/потрогать.
> Это важнее, чем «закончить всё разом через 3 месяца».

Общая длительность MVP: **примерно 3-4 месяца** при работе одного
разработчика на полную ставку.

---

## Спринт 0. Старт (текущий)

**Цель:** договориться, что строим. Без кода.

**Готово:**
- README, ARCHITECTURE, MVP_PLAN, INTEGRATIONS.
- Зафиксированы решения по стеку, источникам, отчётам, multi-tenancy,
  расходам.

## Спринт 1. Скелет проекта (1-2 недели)

**Цель:** запустить пустую систему, в которую можно зайти, создать
аккаунт и подключить iiko.

**Задачи:**

1. Каркас backend (FastAPI + структура папок согласно ARCHITECTURE §13).
2. Каркас frontend (Vite + React + Refine + Mantine, страницы логина,
   регистрации, пустой дашборд).
3. `docker-compose.yml` со всеми сервисами; локальный запуск одной
   командой.
4. PostgreSQL + Alembic; первая миграция.
5. Модели: `Account`, `User`, `Establishment`, `Source`.
6. Auth: регистрация, логин, JWT, защита эндпоинтов, RBAC-роли.
7. Multi-tenant middleware: автоматический фильтр по `account_id`.
8. CRUD-страницы во фронте для заведений и источников.
9. Healthcheck-эндпоинт + базовый логгер.
10. CI-заготовка (lint, тесты, миграции).

**Критерии готовности:**
- `make up` поднимает всё.
- Можно зарегистрироваться, залогиниться, создать заведение, добавить
  источник типа iiko (но синхронизация пока заглушка).

## Спринт 2. iiko: продажи и отчёт «Выручка/чеки» (2 недели)

**Цель:** реальные данные из iiko в системе, первый отчёт.

**Задачи:**

1. Коннектор `iikoCloud`: авторизация, organizations, OLAP-запросы.
2. Модели: `Product`, `Sale`, `SaleItem`, `RawPayload`, `SyncRun`.
3. ETL: миграция данных iiko → унифицированная модель.
4. Celery + beat: периодическая синхронизация (инкремент по дате).
5. UI для запуска ручной синхронизации + индикатор статуса.
6. Сервис отчёта «Выручка/чеки»: запросы, агрегация, сравнение периодов.
7. Страница `/reports/revenue` с фильтрами (период, заведение) и
   таблицей + графиком.
8. Экспорт отчёта в Excel (первый шаблон).

**Критерии готовности:**
- Подключив реальный iiko твоего ресторана, видим в системе чеки за
  последний месяц.
- Отчёт «Выручка/чеки» работает, фильтры работают, выгрузка работает.

## Спринт 3. ABC + Foodcost/маржа (2 недели)

**Цель:** заработала продуктовая аналитика.

**Задачи:**

1. Расширение коннектора iiko: тянем product cost из OLAP.
2. Модель `CostSnapshot`, фиксация `cost_at_sale` в `sale_items`.
3. Сервис отчёта ABC: алгоритм, фильтры.
4. Сервис отчёта Foodcost: формулы, срезы по блюду и категории.
5. Страницы `/reports/abc` и `/reports/foodcost` с таблицами и графиками.
6. Excel-шаблоны для обоих отчётов.
7. Тесты на корректность расчётов (фиксированные fixtures + ожидаемые
   значения).

**Критерии готовности:**
- ABC-анализ показывает корректное распределение по выручке и марже.
- Foodcost по блюду/категории/периоду виден, сравнивается с iiko.

## Спринт 4. Расходы: ручной ввод и CSV (2 недели)

**Цель:** научились вводить расходы в систему.

**Задачи:**

1. Модели: `ExpenseCategory` (дерево), `Expense`.
2. Стартовый набор категорий при создании Account.
3. CRUD API + страницы для расходов и категорий.
4. Импорт CSV/Excel: загрузка файла, маппинг колонок, превью, импорт,
   откат при ошибке.
5. Поддержка распределения расхода между несколькими заведениями.
6. Простой отчёт «Расходы по категориям» (таблица + круговая диаграмма).

**Критерии готовности:**
- Можно вручную внести расход за месяц и увидеть его в отчёте.
- Можно загрузить CSV с десятками расходов и распределить их по
  категориям.

## Спринт 5. P&L и дашборд (2 недели)

**Цель:** полная картина по заведению.

**Задачи:**

1. Сервис P&L: расчёт по формуле «выручка − foodcost − расходы», по
   месяцам/кварталам/годам.
2. Страница `/reports/pnl` с раскрывающейся структурой (по категориям
   расходов).
3. Дашборд `/dashboard`: ключевые KPI (выручка, средний чек, foodcost
   %, чистая прибыль) + графики динамики.
4. Сравнение период-к-периоду везде, где имеет смысл.
5. Excel-шаблон P&L (для отправки бухгалтеру/инвестору).

**Критерии готовности:**
- На дашборде владелец видит «как дела» за текущий и прошлый месяц.
- P&L собирается за любой период и выгружается в Excel.

## Спринт 6. Quick Resto (2 недели)

**Цель:** доказали, что архитектура расширяется на новые POS.

**Задачи:**

1. Коннектор `QuickResto`: авторизация, эндпоинты продаж/продуктов.
2. ETL: маппинг QR-данных в унифицированную модель.
3. UI для подключения QR-источника.
4. Тестирование: ни одна страница отчёта не должна знать, что данные
   из QR — всё работает прозрачно.
5. Если получается — поддержка двух источников на одном заведении
   (один как основной, другой как дополнительный).

**Критерии готовности:**
- Quick Resto подключается и тянет данные так же, как iiko.
- Отчёты работают без изменений.

## Спринт 7+. Расходы из внешних источников

Дальше идём по приоритету пользы:

- **Спринт 7.** Банк (Тинькофф Бизнес или Сбер Бизнес — что есть у
  владельца). OAuth, периодическая выгрузка, правила автокатегоризации.
- **Спринт 8.** МойСклад: тянем документы расходов, маппим в наши
  категории.
- **Спринт 9.** 1С: интеграция через 1С-API (если у пользователя есть)
  или через ODATA.

К этим спринтам мы подойдём, когда базовые сценарии будут отлажены и
понятна реальная польза автоматизации.

## Что НЕ входит в MVP

Чтобы не потеряться, фиксирую границы:

- ❌ Мобильное приложение. Только адаптивный веб.
- ❌ Прогнозы / ML. Только описательная аналитика.
- ❌ Управление меню (изменение тех. карт, цен) — это делается в iiko.
- ❌ Управление складом / закупками — это делается в iiko / МойСкладе.
- ❌ Касса / ОФД — мы не подменяем POS-систему.
- ❌ Мультивалютность — только RUB.
- ❌ Платежи внутри платформы / биллинг — пока продукт не SaaS на
  внешних клиентов.
- ❌ Сложный RBAC с динамическими ролями. Только статический набор
  ролей.

## Метрики успеха MVP

Через 3-4 месяца у владельца должно быть:

1. ✅ Возможность за 30 секунд увидеть выручку, средний чек, foodcost,
   чистую прибыль за выбранный период.
2. ✅ ABC-анализ для принятия решений по меню.
3. ✅ Полностью введённые расходы за тестовый месяц.
4. ✅ Excel-выгрузка P&L для бухгалтера.
5. ✅ Опыт работы с двумя POS (iiko + QR) — подтверждение, что
   архитектура работает.
